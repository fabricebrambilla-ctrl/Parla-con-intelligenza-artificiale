# Task G: phones

Status: **implemented, awaiting real-user confirmation**. No physical iPhone/VoiceOver or Android/TalkBack verification was possible here. This is a mitigation of competing speech, not detection or cancellation of screen-reader audio.

## G1: recording after a touch gesture

`public/app.js`, input-event mute gate and `startRecording`: feature-based `IS_TOUCH` detection is retained. Phone input now uses the existing 1,500 ms mute period instead of the desktop Talk shortcut's 300 ms. After the microphone is ready, phone recording waits at least 1,500 ms, extended if further input renews the mute period. No frames, start tone or vibration occur during that wait. The tone and vibration occur together when recording begins. The original desktop timing remains unchanged. Session/request checks cancel stale starts; a removed microphone returns to ready or resolves the language recording instead of leaving it waiting.

Tests: phone start cue and cancellation, removed microphone and language-recording completion fail on the original code and pass after implementation; desktop immediate recording passed before and after. A real user must judge whether 1.5 seconds is sufficient at their reader speed and whether the cue still clearly means “speak now”.

## G2: avoid page announcements during playback

`public/app.js`, `afterSpeech`, `setState`, `say`, `renderTexts`, `showConversationControls`, last-answer helpers and language/microphone handlers: queue non-error announcements, Copy status, label/ARIA changes and programmatic focus work while state is speaking. Playback completion transitions out of speaking and flushes work belonging to the same session. Ended-session updates are discarded. Error announcements remain allowed. Native keys are not replaced; Escape propagation remains handled synchronously.

Tests: Copy, conversation labels, translated labels, non-error status, delayed status and actual speech-completion flushing fail before and pass after. A real user must verify that the page no longer triggers unwanted reader speech during answers, including Copy and language controls. The page cannot prevent speech caused by the user navigating their screen reader or other apps.

## G3: keep Talk available after answers

`goReady` changes state before updating the Talk label. It avoids rewriting the label after its initial change and does not refocus an already focused Talk button. It restores focus only when the foreground document has lost it to body/documentElement; intentionally selected End, Copy, Language, links and other controls are preserved. Pending interruption uses the same path before starting capture.

Tests invoke real completion paths for normal answer, nothing heard, retry, language switch, showing the last answer, a page command and pending interruption. Lost-focus checks fail before and pass after; preservation of chosen controls passes. Real readers must confirm focus announcements and virtual/touch-cursor position; DOM focus alone cannot establish this.

## G4: optional headphones advice

`public/i18n.js` adds one sentence only to touch first-use greeting and touch spoken help in en, it, fr, bg, ru, zh, ja, nl and European Portuguese (pt-PT). `runCommand` selects touch help with `tk`. English: “On a phone, headphones can help keep the screen reader and assistant audio from overlapping.” Dutch/Portuguese remain gated by the existing setting; they were not enabled in production.

The all-nine-language check fails before and passes after. Native speakers and blind phone users must confirm wording and practical usefulness. No headphones are required by the code.

**Owner decision pending:** the question about changing the existing “No headphones and no special settings are needed” accessibility sentence was asked. `legal.js` is deliberately unchanged pending that answer; no choice has been inferred.

## G5: speech speed report only

`speakBrowser` constructs `SpeechSynthesisUtterance` without setting `.rate`, so it uses the Web Speech default rate of 1. Actual speed depends on the selected voice. `fishSpeak` sends text, MP3 format and an optional reference voice ID; no speed/prosody override is sent. The speed and controls are unchanged. A real iPhone user must listen before any change is proposed.

## G6: current iPhone permission instructions, unchanged

The first English spoken permission sequence is: “To hear you, I need the microphone. Your browser will now ask for permission. Choose Allow. With a touch screen reader, find Allow, then double-tap it.” On a return visit requiring permission: “The browser now asks for the microphone. Choose Allow.” The existing AI disclosure/agreement precedes it. Other site languages use their localized equivalents.

The existing focused explanation and 2–4.5 second pause are preserved. Nothing here promises persistence on iOS or attempts to operate the browser prompt. No demonstrated factual error in these gesture instructions was identified; further simplification belongs to Task H, not this commit. Real iPhone VoiceOver testing must verify finding Allow, the gesture, prompt language, pause and return focus.
